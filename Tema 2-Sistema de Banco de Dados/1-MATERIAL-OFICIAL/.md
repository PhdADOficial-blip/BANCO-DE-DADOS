### 🧩 BLOCO 1 — Histórico e Evolução dos Sistemas de Informação

**🔵 TEORIA — a linha do tempo que você precisa guardar**

```
Computador (1940, cálculos) 
   → Arquitetura de von Neumann (CPU + memória guardam dados E programas juntos)
   → Disco magnético / HD (IBM, 1957) → acesso direto, não sequencial
   → Sistema de Arquivos (programas com módulo de gerência de arquivo embutido)
   → PROBLEMA: cada programa repete a lógica de acessar o arquivo
   → SBD (a partir de 1960): um software (SGBD) assume essa responsabilidade
   → Modelo Relacional (Edgar Codd, 1970): dados = tabelas (relações matemáticas)
   → Middleware / Web (fim séc. XX): SGBD vira "back end" de aplicações web
   → Big Data / NoSQL: bancos não relacionais para dados massivos e variados
```

**Conceito-chave nº 1: Independência entre dados e programas**
- Antes do SBD: o programa "sabe" como o arquivo está organizado fisicamente.
- Depois do SBD: o programa pede dados ao SGBD, e o SGBD decide como buscar. O programa não precisa saber onde/como os dados estão fisicamente guardados.
- **Por que isso importa (elaboração):** imagine que você muda o HD de lugar ou reorganiza os arquivos — sem essa independência, todo programa quebraria. Com ela, só o SGBD precisa se ajustar.

**Conceito-chave nº 2: SBD ≠ SGBD (isso cai em prova, decore a diferença)**

| SBD (Sistema de Banco de Dados) | SGBD (Sistema de Gerência de BD) |
|---|---|
| É o conjunto **completo**: dados + programas de aplicação + SGBD | É o **software intermediário** dentro do SBD |
| Conceito mais amplo | Componente específico, o "motor" |
| Exemplo: todo o sistema de matrícula de uma faculdade | Exemplo: o PostgreSQL rodando por trás desse sistema |

**Modelos de banco de dados na história:**

| Modelo | Época | Estrutura de dados | Exemplos |
|---|---|---|---|
| Navegacional (rede) | 1960 | Grafo/rede (CODASYL) | IDS |
| Navegacional (hierárquico) | 1960 | Árvore | IMS (IBM) |
| **Relacional** | 1970 | Tabela (relação matemática) | Oracle, MySQL, SQL Server, PostgreSQL, DB2 |
| Não relacional (NoSQL) | Atual | Chave-valor, documentos, grafos, colunar, etc. | MongoDB, Redis, Neo4j, Cassandra |

**🟢 PRÁTICA:** Nada de comandos ainda neste bloco — é fundamentação. Mas guarde: quando você abrir o PostgreSQL nos próximos temas, vai estar usando um SGBD **relacional-objeto**, herdeiro direto do projeto acadêmico Ingres (Berkeley) → Postgres → PostgreSQL.

**🟠 MERCADO:**
- A menção a COBOL e "sistemas legados" não é decoração histórica — é real: bancos, governos e seguradoras ainda rodam sistemas de arquivos/navegacionais de décadas atrás. Por isso "programador COBOL" ainda é procurado (e bem pago) em manutenção de sistemas legados.
- Quando alguém falar em "middleware" ou "back end" numa entrevista, você já sabe: é o papel que o SGBD (ou uma API) exerce entre a aplicação e os dados.
- Saber a diferença entre SQL (banco relacional) e NoSQL é pergunta comum em entrevistas técnicas júnior.

### 🧩 BLOCO 2 — Características dos Sistemas de Banco de Dados (SBD)

**🔵 TEORIA — Arquitetura de Três Esquemas (ANSI/SPARC)**

```
Nível Externo    → visão de cada usuário/aplicação (o que ele "enxerga")
Nível Conceitual → estrutura lógica completa do banco (visão do projetista)
Nível Interno    → como os dados são fisicamente armazenados em disco
```

Dessa arquitetura nascem **dois tipos de independência**:

| Tipo | O que permite mudar | O que NÃO é afetado |
|---|---|---|
| **Independência lógica** | Mudar o esquema conceitual (ex.: adicionar uma coluna) | As visões externas dos usuários |
| **Independência física** | Reorganizar os arquivos físicos em disco | O esquema lógico e as visões externas |

**Técnica de Feynman aplicada:** pense em uma casa (nível interno = fundação e encanamento), a planta arquitetônica (nível conceitual = como os cômodos se relacionam) e o que cada morador vê no seu quarto (nível externo). Trocar o material do cano (física) não muda a planta. Adicionar um cômodo na planta (lógica) não precisa mudar o que o morador do quarto ao lado vê.

**3 características que diferenciam SBD de sistemas de arquivos (decore estas — caiu em atividade no material):**

1. **Natureza autocontida** → o SBD guarda, além dos dados, a descrição completa da própria estrutura (isso é o **metadado**, guardado no **catálogo do sistema**).
2. **Abstração de dados** → esconde detalhes de armazenamento físico, permite múltiplas visões lógicas.
3. **Suporte a compartilhamento e transações concorrentes** → vários usuários acessam ao mesmo tempo.

> ⚠️ Pegadinha de prova: "volatilidade dos dados" e "armazenamento de dados estáticos" **NÃO** são características do SBD — aparecem como distratores nas atividades do PDF.

**Modelos de dados — os 3 níveis de abstração:**

| Modelo | O que representa | Exemplo |
|---|---|---|
| **Conceitual** | Visão do usuário final, mais próxima do mundo real | Modelo Entidade-Relacionamento (Peter Chen, 1976) / UML |
| **Lógico** | Estrutura abstrata de implementação | Modelo Relacional (tabelas) |
| **Físico** | Como os dados ficam armazenados no disco | Tipos de arquivo, índices, ordenação |

**🟢 PRÁTICA:** Este bloco é a ponte para o próximo tema da disciplina: "Modelagem conceitual" (Entidade-Relacionamento) e "Modelagem lógica/física" (normalização). O que você está lendo agora é a base teórica que vai justificar por que você vai desenhar diagramas ER depois.

**🟠 MERCADO:** Quando um recrutador pergunta "você sabe o que é independência de dados?", ele quer ver se você entende por que empresas conseguem trocar de servidor, reorganizar índices ou migrar de banco sem reescrever todo o sistema. Isso é usado para justificar decisões de arquitetura de software no dia a dia.

### 🧩 BLOCO 3 — Vantagens, Desvantagens e Propriedades ACID

**🔵 TEORIA — Funcionalidades do SBD**

| Funcionalidade | O que resolve |
|---|---|
| Controle de redundância | Evita dados duplicados e inconsistentes |
| Compartilhamento de dados | Múltiplos usuários, com controle de concorrência |
| Controle de acesso | Senhas, permissões, restrições por usuário/grupo |
| Múltiplas interfaces | Linguagens de consulta, GUIs, APIs, linguagem natural |
| Representação de relacionamentos | Liga dados entre si conforme o mundo real |
| Restrições de integridade | Tipo de dado, chaves únicas, integridade referencial |
| Backup e recuperação | Restaura o banco após falhas |

**Propriedades ACID (decore a sigla — é cobrada sempre)**

| Letra | Propriedade | Definição resumida |
|---|---|---|
| **A** | Atomicidade | A transação executa por completo ou não executa nada (tudo ou nada) |
| **C** | Consistência | A transação leva o banco de um estado válido para outro estado válido |
| **I** | Isolamento | Transações concorrentes não interferem umas nas outras |
| **D** | Durabilidade | Uma vez confirmada (commit), a transação sobrevive a falhas do sistema |

**Elaboração (Feynman):** pense numa transferência bancária (retirar de A, depositar em B).
- **Atomicidade:** se der erro depois de retirar de A, o sistema desfaz tudo — o dinheiro não "some".
- **Consistência:** o saldo total do banco antes e depois bate.
- **Isolamento:** se duas pessoas mexerem na mesma conta ao mesmo tempo, uma não vê o resultado incompleto da outra.
- **Durabilidade:** depois que a tela mostra "transferência concluída", mesmo que o servidor caia no segundo seguinte, o dinheiro já está lá.

**Vantagens vs. Desvantagens**

| Vantagens | Desvantagens |
|---|---|
| Padronização de dados na organização | Overhead de desempenho (o SGBD é uma camada extra) |
| Menos tempo de desenvolvimento | Custo de licença, hardware e capacitação |
| Flexibilidade de manutenção | Complexidade de administração |
| Dados sempre atualizados para toda a empresa | — |

**Quando NÃO usar SBD:** aplicações muito simples e estáticas, sistemas de tempo real crítico (ex.: piloto automático), sistemas embarcados, monousuário sem concorrência.

**🟢 PRÁTICA:** No PostgreSQL (próximos temas), você vai literalmente usar comandos `BEGIN`, `COMMIT` e `ROLLBACK` para controlar transações — isso é ACID sendo aplicado na prática.

**🟠 MERCADO:** ACID é **pergunta clássica de entrevista** para vagas de backend/dados. Também é usado para justificar escolha entre banco relacional (forte em ACID) e NoSQL (muitos sacrificam parte do ACID em troca de escalabilidade — conceito conhecido como BASE/teorema CAP, que você provavelmente vai encontrar depois).

### 🧩 BLOCO 4 — Arquitetura do SGBD e Papéis dos Usuários

**🔵 TEORIA — Papéis em um Sistema de Banco de Dados**

| Papel | Função |
|---|---|
| **Administrador de dados** | Define políticas, regras de negócio e padrões de dados da organização (gerencial) |
| **Administrador do Banco de Dados (DBA)** | Cria e mantém os bancos no SGBD (técnico) |
| **Administrador de aplicações** | Mantém os sistemas de aplicação e dá suporte aos usuários |
| **Administrador de desenvolvimento** | Coordena as equipes que constroem os sistemas |
| **Administrador de sistema** | Cuida do hardware/SO/infraestrutura |
| **Usuários finais** | Os beneficiários do sistema (quem usa no dia a dia) |

> Uma pessoa pode acumular vários papéis (empresas pequenas) ou cada papel pode ser um departamento inteiro (empresas grandes).

**Módulos internos de um SGBD (o "miolo" que você precisa entender, não decorar cada caixinha)**

```
Usuários → [DBA | Usuários casuais | Programadores | Usuários paramétricos]
              ↓            ↓               ↓                 ↓
        Comandos DDL   Consulta ad hoc  Programas de     Transações
        e DCL          (SELECT)         aplicação (DML)  compiladas
              ↓            ↓               ↓                 ↓
                    → PROCESSADOR DE RUNTIME (o "coração" do SGBD) ←
                              ↓                    ↓
                    Catálogo do sistema      Banco de dados
                    (metadados)              armazenado (dados)
```

**As 3 linguagens que você vai usar em SQL (isso é fundamental para os próximos temas):**

| Sigla | Nome completo | Para quê serve | Comandos |
|---|---|---|---|
| **DDL** | Data Definition Language | Criar/alterar/remover estruturas (tabelas) | `CREATE`, `ALTER`, `DROP` |
| **DML** | Data Manipulation Language | Manipular os dados dentro das tabelas | `SELECT`, `INSERT`, `UPDATE`, `DELETE` |
| **DCL** | Data Control Language | Controlar permissões de acesso | `GRANT`, `REVOGAR` (`REVOKE`) |

> 🎯 **Isso é o gancho direto para o Tema 4 da sua disciplina** ("Criar e manipular objetos no PostgreSQL"). Quando você chegar lá, vai reconhecer imediatamente que `CREATE TABLE` é DDL e `INSERT INTO` é DML.

**Estado/Instância vs. Esquema (diferença sutil, mas cobrada):**
- **Esquema** = a estrutura (tabelas, colunas) — muda raramente.
- **Estado/instância** = o conteúdo armazenado num momento específico — muda a cada INSERT/UPDATE/DELETE.

**🟢 PRÁTICA:** Toda vez que você abrir um SGBD, vai estar interagindo com esse fluxo: você (usuário casual ou programador) manda um comando → ele passa por um compilador/otimizador → chega ao processador de runtime → acessa catálogo e dados.

**🟠 MERCADO:** Saber a diferença entre DDL, DML e DCL é básico e frequentemente testado em testes técnicos de vagas júnior de dados/backend. Também: em empresas reais, "DBA" é um cargo específico — geralmente sênior, focado em performance, segurança e disponibilidade do banco, diferente de "desenvolvedor backend" que usa o banco mas não o administra.

### 🧩 BLOCO 5 — PostgreSQL na Prática

**🔵 TEORIA**
- PostgreSQL é um SGBD **relacional-objeto**: estrutura base é a tabela, mas com extensões de orientação a objetos (herança de tabelas, tipos customizados).
- Modelo de computação: **cliente/servidor**.
  - **Back end** = processo `postgres`, gerencia os arquivos e conexões.
  - **Front end** = aplicações clientes (`psql`, `pgAdmin`, ou qualquer app que se conecte).
- Possui **todas** as propriedades ACID.
- Licença **open source (BSD)** — pode usar, modificar e distribuir livremente.

**🟢 PRÁTICA — o que você vai realmente instalar/usar em breve**
- **psql**: interface de linha de comando.
- **pgAdmin**: interface gráfica.
- Recursos que você vai usar nos próximos temas: `CREATE TABLE`, chaves estrangeiras, índices, `SELECT` com filtros e junções.

**🟠 MERCADO**
- PostgreSQL é hoje um dos SGBDs mais requisitados no mercado (junto com MySQL) justamente por ser gratuito, robusto e ter documentação de referência mundial.
- Empresas de todos os tamanhos usam — de startups a bancos e órgãos públicos.
- Saber PostgreSQL é transferível: a lógica SQL que você aprender aqui serve, com pequenos ajustes de sintaxe, para MySQL, SQL Server e Oracle também.
